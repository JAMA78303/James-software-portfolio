Matching how someone feels to the right ayah

James MachmouchiOctober 2026TypeScript · Vitest · Supabase

In the Dua & Ayah Companion, people type how they feel in their own words, and the app opens an ayah or dua for that feeling. This is how I rebuilt the matcher so that “I'm not sad, just really anxious about my exams” lands on anxiety instead of sadness.

Uses the app's built-in keywords plus the five database keywords from the test file. The live app also loads the full keyword table from Supabase.

The problem

The app has eleven feelings, such as anxiety, grief, guidance and anger, and each one has its own collection of ayat and duas. The search box has one job: read a sentence and pick the right feeling. I set a few constraints:

  • Private. People write very personal things here. The text should never leave their phone.
  • Instant and free. No round trip to an AI model, and no per-search cost.
  • Explainable. When it picks the wrong feeling, I need to see exactly why and fix it with a test.
  • Editable without a deploy. Content reviewers can add keywords in a Supabase table.

What was wrong with the first version

The first matcher checked a list of regex “overrides” first, then picked the single heaviest keyword it found. Real sentences broke it in three ways:

InputGotWhy
“I'm not sad, just anxious”sadnessThe /\bsad\b/ override fired first. It had no idea about “not”.
“I can't sleep”nothingThe input became i can t sleep, but the database keyword was i can't sleep. Keywords with apostrophes could never match.
Any text, database downnothingA failed keyword fetch threw an error, so the search silently did nothing.

How the new matcher works

  1. Normalise both sides the same way. Lower-case, drop apostrophes, turn punctuation into spaces. “I can’t sleep!” and the keyword i can't sleep both become i cant sleep. This one change fixed every database keyword with an apostrophe.
  2. Match whole words, including phrases. Slide each keyword along the tokens. “hope” matches hope but not hopeless, which has its own entry under the same feeling at a higher weight.
  3. Ignore negated keywords. If “not”, “don't”, “never” or another negator appears in the three words before a keyword, that keyword doesn't count.
  4. Add up every match per feeling. Each keyword has a weight between 0.6 and 1. Phrases weigh more than single words, so “passed away” (1.0) is a stronger signal than “loss” (0.8).
  5. Pick the highest total. If nothing scores, return null and the app offers “browse by feeling” instead of guessing.

The core is one pure function, which makes it easy to test:

export function scoreIntent(input: string, mappings: IntentMapping[]): EmotionCategory | null {
  const tokens = normaliseForMatching(input).split(" ").filter(Boolean);
  if (tokens.length === 0) return null;

  const scores = new Map<EmotionCategory, number>();
  for (const mapping of mappings) {
    const keyword = normaliseForMatching(mapping.keyword).split(" ").filter(Boolean);
    if (keyword.length === 0) continue;
    for (let i = 0; i + keyword.length <= tokens.length; i++) {
      if (!keyword.every((word, k) => tokens[i + k] === word)) continue;
      // A negator in the three words before the keyword cancels it ("I'm not sad")
      const negated = tokens.slice(Math.max(0, i - NEGATION_WINDOW), i).some((t) => NEGATORS.has(t));
      if (!negated) scores.set(mapping.category, (scores.get(mapping.category) ?? 0) + mapping.weight);
    }
  }

  let best: EmotionCategory | null = null;
  let bestScore = 0;
  for (const [category, score] of scores) {
    if (score > bestScore) { best = category; bestScore = score; }
  }
  return best;
}

Around it, matchIntent loads the keyword table from Supabase, merges it with the built-in keywords and caches it for five minutes. If the database can't be reached, it falls back to the built-in keywords, so the search still works.

A worked example

“I lost my job and I'm so stressed” contains two signals:

  • lost → guidance, 0.6
  • stressed → anxiety, 0.9

Anxiety wins, 0.9 to 0.6. Now compare “I lost someone close to me”: the database phrase i lost someone scores grief 1.0, beating guidance at 0.6. Same word, different feeling, and the reason is visible in the numbers. Type either sentence into the demo above to see the breakdown.

Testing it

Every failure I found became a test before I fixed it. The suite has 6 Vitest tests covering apostrophes, negation, phrases beating single words, everyday phrasing, anger, and inputs that should match nothing. They run in under 10 ms because scoreIntent is a pure function with no database or network:

it("ignores negated feelings", () => {
  expect(match("I'm not sad, just really anxious about my exams")).toBe("anxiety");
  expect(match("I don't feel lonely anymore, I'm grateful")).toBe("gratitude");
  expect(match("there is no hope")).toBe("hope");
});

The last line is deliberate. “No hope” is itself a keyword for the hope feeling, which holds ayat for people who feel hopeless. The phrase match has nothing before it, so it isn't negated, and the person still gets the right collection.

Trade-offs and what I'd do next

  • Why not an AI model or embeddings? They would handle more phrasing, but they'd send private text to a server, add cost and delay, and make wrong answers hard to explain. For eleven feelings, weighted keywords plus tests cover common sentences well, and every result can be traced.
  • Mixed feelings. “Grateful but exhausted” returns one feeling. Showing the top two when scores are close would be more honest.
  • Spelling. “anxios” won't match. A small edit-distance check on single words would catch common typos.
  • Learning from misses. Without logging what people write, the app could count how often each result is followed by “browse by feeling”. That would show which feelings need more keywords, without storing anyone's words.
